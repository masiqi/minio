# D087｜项目答辩与需求变化验收

[目录](README.md) · [原教学卡](../daily/D061-D090-agent-production.md) · M09 · 前置：[D086](D086.md)

## 预习：复习地图

真正掌握架构，要能在变化后解释哪些假设失效、哪些组件受影响、如何最小修改与验证。准备业务目标、机制、边界、成本、可靠性、安全六个视角，而不是背一份固定 Demo 台词。

## 核心框架与案例

本次预习情境：系统增加“写操作必须二次批准”。先定位现有批准对象、状态机、执行器与恢复路径；再确认参数绑定和幂等是否受影响；最后更新测试与 Runbook。不能只在 prompt 中加一句“记得批准”就宣布完成。

其他变化可能是租户规模、文档删除要求、模型替换。每次区分必须改变与可以保持的接口，用原有契约测试证明局部改动没有破坏其他行为。

答辩应引用真实项目产物与测量，明确尚未实现或未测的范围。承認不确定并提出验证方法，比用更多术语填空更有价值。

## 易错边界

能展示既定路径不等于能应对新约束。说“加缓存/换模型/上微服务”不解释目标和失败边界，不能算完整方案。单项失败只回补相关能力，不自动抹掉全部成果。

## 复习：先独立回答

1. 需求变化后，为什么先查原假设和契约，而不是立即重写架构？
2. 怎样证明最小修改仍满足安全和恢复要求？

<details><summary>展开核对要点</summary>

找到真实受影响边界可减少无关复杂度和回归。通过新约束测试、已有回归、故障窗口及环境 outcome 核验，并更新证据和未解决项。

</details>

## 动手与达标证据

完成 Demo 后接受一个未见约束，独立提出修改、风险与测试，并实现可控一项。公开例子只供准备，正式题需更换。
