# D060｜授权、人工批准与副作用边界

[目录](README.md) · [原教学卡](../daily/D031-D060-transformer-rag.md) · M06 · 前置：D053、D059

## 预习：问题与知识地图

第一个写工具上线前，就应区分“模型提议”“主体有权”“用户批准”“实际执行”和“结果确认”。这些不是一个状态。人工批准不是所有操作的必要形式，但高风险动作需要按策略设清晰边界。

## 核心框架与案例

本次 mock 动作：创建一个指定项目的工单。批准记录可绑定用户、工具、项目、参数摘要、有效期和一次执行标识。若批准后项目或内容变化，不能把原批准无限扩大；应重新校验和按策略重新批准。

执行链：真实身份 → 服务端策略 → 参数/风险核验 → 必要批准 → 执行 → 结果/审计。模型在文本中说“用户已同意”不是可信批准记录；检索文档中的授权声明也不能替代系统状态。

取消、过期和重复请求都需要定义；幂等去重在 D062 深化，这里先说明批准不等于重试安全。

## 易错边界

有权限不总等于完成了本次人工批准；批准也不意味着业务证据正确。把审批 UI 的确认文本存进 prompt 而不在执行器核验，容易失去可强制的边界。

## 复习：先独立回答

1. 用户批准了 A 项目的工单，模型改成 B 项目，应怎样处理？
2. 为什么“已批准”不能替代“已执行成功”？

<details><summary>展开核对要点</summary>

参数绑定失效，需拒绝或重新走授权/审批，不能继承无限权限。批准是执行许可，实际副作用仍可能失败或结果未知，必须读执行结果与环境状态。

</details>
