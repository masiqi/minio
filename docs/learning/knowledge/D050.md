# D050｜Query 改写、Reranking 与召回/精排分工

[目录](README.md) · [原教学卡](../daily/D031-D060-transformer-rag.md) · M05 · 前置：[D049](D049.md)

## 预习：问题与知识地图

召回负责让相关证据进入候选，精排负责在已有候选中排序；改写负责使查询意图更适合检索。三者作用不同，不能用“调整 Top-K”代替所有诊断。

## 核心框架与案例

本次对话：“这个方案支持吗？”改写前需要解决“这个方案”指什么，但不能擅自加入用户没说的国家、版本或预算。保留原 query、改写 query 和来源上下文，便于诊断语义漂移。

假设 retrieval K=20，reranker 重排20项，最终 context K=4。正确文档排第15时，精排可能改善；正确文档根本不在20项中，单纯重排无法把它创造出来。增加候选可以提高覆盖机会，也会增加精排开销与噪声。

评价时分开看相关证据是否进入候选、进入后排名是否合适、最后是否被选进 Context，不能把这些失败全部算到生成层。

## 易错边界

Reranker 不是事实验证器，也不能恢复未召回的证据。改写看起来语法更好不等于保留原意。Context K 和 retrieval K 相同并非必要，甚至可能浪费输入预算。

## 复习：先独立回答

1. 正确证据未进入第一阶段候选，应先检查哪里？
2. 为什么必须保存改写前后的问题，而不是只保存最终 prompt？

检查 query、解析、切块、索引、召回策略和权限过滤；不是只调 reranker。原始与改写记录帮助发现凭空增加条件、丢失限制和错误指代。

## 动手与达标证据

固定候选比较原排序与精排；另对改写做意图约束测试。报告召回失败、排序失败和上下文选择失败三类。衔接：[D051](D051.md)；依据：[S16](SOURCES.md#s16)。
