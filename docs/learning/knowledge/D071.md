# D071｜Harness 的职责与可替换边界

[目录](README.md) · [原教学卡](../daily/D061-D090-agent-production.md) · M07 · 前置：D064、D070

## 预习：问题与知识地图

沿用本项目定义，Harness 是围绕模型的执行支撑层，不是一个固定产品名。它组织 Context、工具适配、状态、恢复、预算、策略和观察/评价入口。模型、编排框架、MCP、Harness、Sandbox 分属不同职责，不能互相代称。

## 核心框架与案例

本次替换场景：将模型 A 换成模型 B。若应用契约清晰，主要修改 provider adapter 和能力校验；工具的授权、幂等、持久状态与隔离不应因模型更强而被删除。仍需用相同任务集验证格式、工具建议和质量变化。

另一种替换是将本地工具改为 MCP server；协议适配变化，但业务契约可以保持。换 Sandbox 则影响执行环境和资源策略，不应要求重写所有提示词才能保持权限。

以依赖方向检验架构：业务需求通过稳定接口调用能力，具体 SDK/模型/环境是可替换实现；若更换一个组件牵动所有状态与审批逻辑，应分析耦合是否必要。

## 易错边界

把所有代码放在名为 harness 的目录，不等于职责清楚。MCP 不提供整个任务循环，Sandbox 不决定业务目标，模型输出也不替代确定性策略。更强模型仍可能提出无权动作。

## 复习：先独立回答

1. 更换模型后，哪些安全和可靠性测试必须继续存在？
2. 为什么 MCP server 与整个 Harness 不应直接画等号？

<details><summary>展开核对要点</summary>

授权、审批、幂等、恢复、预算、隔离与真实 outcome 等仍应验证。Server 只承担特定协议能力与业务实现，完整任务的状态、模型交互及策略编排还在其他组件。
