# 每日学习文档标准（Daily Learning Document Standard）

每个 Day 文档都应当是一个**可以独立使用的学习单元**。即使读者没有参与当天对话，只阅读 Markdown，也应该知道“为什么学、学什么、怎么学、如何验证、达到什么程度才算通过”。

## 必须包含的结构

1. **今日定位**：本主题在整体知识路线中的位置，以及为什么现在学习它。
2. **前置知识**：开始前需要理解什么；不要求掌握什么。
3. **学习目标**：使用可验证的能力描述，避免只写“了解 / 熟悉”。
4. **为什么需要这个知识**：从问题、旧方案局限和工程动机建立因果链。
5. **核心心智模型**：用直觉模型解释机制，并明确类比的边界。
6. **核心机制**：逐步说明信息如何流动、组件分别做什么、因果关系是什么。
7. **关键概念与区别**：重点处理容易混淆的概念。
8. **常见错误模型**：记录典型误解，以及为什么错、正确模型是什么。
9. **工程映射**：只有存在真实联系时，映射到 Agent / RAG / MCP / Context / Memory / Sandbox 等工程场景。
10. **主动练习**：安排主动回忆、解释题、推理题或小实验，而不是只提供阅读材料。
11. **费曼验证**：要求学习者不用笔记，用自己的话解释核心因果链。
12. **追问验证**：使用 1–3 个问题检查边界条件、反例、机制或工程迁移。
13. **达标标准（Acceptance Criteria）**：明确最低通过标准，至少覆盖 Concept、Mechanism、Engineering、Interview Expression 中与当天主题相关的维度。
14. **当天实际结果**：记录学习者已经掌握的内容、暴露的问题和纠正过程；计划与实际结果必须区分。
15. **复习计划**：记录需要再次主动回忆的内容和触发条件 / 日期。
16. **下一天衔接**：解释今天的知识如何成为下一主题的前置条件。

## 写作要求

- 默认中文，关键英文技术术语保留。
- 不是聊天记录摘要，而是可重复使用的学习资料。
- 不机械追求篇幅；详细程度服务于独立学习和复习。
- “通过”必须有证据：独立解释 + 针对性追问；不能因为看过或能复述术语就判定掌握。
- 计划内容与学习后结果分开书写，避免把尚未验证的理解写成“已掌握”。
- 对公式和数学：先解释每一项为什么存在，再进入计算。
- 对类比：明确哪些部分是帮助理解的 analogy，哪些部分才是真实机制。
- 对工程映射：只在存在真实技术联系时使用，不强行类比。

## 推荐的达标描述

不要写：

> 理解 Attention。

应该写成可验证形式，例如：

> 不看笔记，能够在 2 分钟内解释 RNN 长距离依赖为什么存在结构性困难；能够说明 LSTM/GRU 改善了什么但没有改变什么；能够解释 Attention 如何改变 information path；面对“Attention 是否让序列长度没有成本”的追问能够指出边界。

后续 Day 2、Day 3……均按照本标准创建和维护。
